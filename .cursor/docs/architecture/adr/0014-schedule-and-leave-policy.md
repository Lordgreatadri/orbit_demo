# ADR-0014: Schedule work periods and leave entitlement

- Status: Accepted
- Date: 2026-11-09

## Context

Schedule stored one assignment per person per date, and leave entitlement was `leave_types.default_days` for every person. ORBIT has to serve office, remote, field, and hybrid work, and tenants whose leave depends on category, grade, employment type, or service. Schools use the same workforce core. A school-specific code path is not acceptable.

The attendance engine already decides check-in. Schedule and leave must give it context.

## Decision

- A shift assignment is one expected work period. The unique key is `(organization_id, staff_member_id, work_date, shift_id)`. Overlapping clock times are rejected in the schedule service. Adjacent periods do not overlap: 09:00–12:00 and 12:00–17:00 are kept, and 09:00–13:00 with 12:00–17:00 is refused. A second, non-overlapping shift on the same date is allowed.
- Assigning a period copies `starts_at`, `ends_at`, and `crosses_midnight` onto the assignment. A later edit of the shift template does not rewrite that snapshot, so historical attendance stays explainable. A past assignment, and an assignment that already has a check-in, cannot be removed.
- Each assignment stores the work arrangement and the expected location. Arrangement `kind` is `office`, `remote`, `field`, or `flexible`. The tenant chooses the name. Office, Remote, Field, and Flexible are created when the organisation workspace is provisioned, and again by an explicit action on Schedules. Opening the page does not insert them. Hybrid work is a week of different arrangements, not a separate engine. The person's standing work type does not override a published period.
- A work pattern is a weekday template. Applying it writes assignments and skips the tenant non-working calendar. The assignment remains the historical fact.
- The attendance engine reads the published period that contains the check-in time. If none contains it, the soonest later period is used only when its start is within `workforce_policies.grace_minutes`. A period that has already ended is not selected. Office and field periods do not use the person's standing remote or hybrid flag to skip a geofence. Remote and flexible periods may, when the organisation policy allows check-in without a geofence. When the assignment has an expected location, that location is the one that is checked. A different `location_uuid` in the request is rejected. A check-in that is not part of a QR session is stored as `period_key` `shift:{assignment id}` on the assignment's work date, so two periods on one date can each have a record. A session check-in keeps the session key.
- Check-out and the My attendance page include an open record whose work date is yesterday when that assignment's scheduled end falls on a later date. Missing-checkout cleanup waits until that scheduled end has passed. A daytime shift from a previous date is still closed on the next calendar day. Checkout punctuality uses the attendance record's assignment. A record with no assignment falls back to the period that contains the checkout time, then to the policy window.
- Leave approval still covers the counted dates for that request. The engine writes and clears `source = leave` attendance rows only when that row has no check-in. Leave does not decide present or late. A request that crosses a leave year is refused; the person submits one request for each year.
- A leave policy sets the leave-year start, whether days are calendar or working days, the weekend, and who may approve. The leave year ends the day before the next configured anchor, including a 29 February anchor that does not exist in a non-leap year. `year_start_month` and `year_start_day` cannot change while that leave type has a balance or a submitted or approved request. Other policy fields can still change. The approval queue uses the same mode as the decision: line manager only when that mode is set, department head only when that mode is set, and a missing relationship leaves the request visible to any approver. An approver can open another person's approved request and cancel it. A `leave.policy` holder sees every request. Entitlement rules are ordered by `priority` ascending, then `id` ascending. The first rule whose filled criteria match wins. A blank criterion matches everyone. Months of service are measured from `started_on` to the period start, and a future start date counts as zero months. Nothing matches falls back to `leave_types.default_days`. A catch-all rule must use a higher priority number than a specific rule. ORBIT does not compute specificity. Later rule edits do not change an open balance. An authorised adjustment is a separate audited row and cannot take `pending_days + used_days` above `entitled_days + adjusted_days`.
- Pending days are reserved at submit. Approval moves them to used inside a transaction that locks the person, rechecks overlap, and refuses self-approval unless the policy allows it. PostgreSQL and MySQL also enforce that balance inequality with `leave_balances_within_entitlement`. SQLite cannot add a check constraint with `ALTER TABLE`, so the test suite proves the service check on one connection. Two PHPUnit processes cannot share the in-memory database, so a true parallel lock is not what that test executes.
- `leave.policy` is separate from `leave.approve`. After the self-approval check, a `leave.policy` holder may decide a request even when the approval mode names a line manager or department head. When that relationship is unset, any `leave.approve` user may decide.
- Schedule and leave notices are dispatched after the database commit on `DeliverWorkforceNotice`, with a stable dedupe key. Inbox, tenant policy, personal preferences, and templates are ADR-0015. That job's middleware saves the current tenant, runs as the notice's organisation, and restores the previous tenant on success and on failure. Queue listeners do not clear the tenant around the job, because a sync queue runs inside the request that dispatched it. Mail and the database notice are sent inside the job. `workforce_notice_deliveries` is unique on recipient, dedupe key, and channel (`notice` or `push`). The claim is written before the send. A completed claim is not sent again, so a queue retry does not create another logical notice. A thrown send deletes that claim so a failed attempt can retry. Mail and the push plug do not accept an idempotency key. If the provider accepted the message and the client then timed out, that retry can deliver it again. External delivery is therefore at-least-once in that acknowledgement gap, not exactly-once. SMS receives the same dedupe key as `sms_messages.idempotency_key`, so a second transmit reuses that row. The HTTP adapters behind `DeliverSmsMessages` do not take a provider idempotency key, so the same acknowledgement gap applies to the upstream send. A later business action uses a new key. A failed SMS send is reported and does not fail the leave or schedule action. The provider HTTP call remains `DeliverSmsMessages`. Switching among registered SMS providers is configuration. A new vendor still needs an adapter.
- Removing an assignment locks the person row, locks the assignment, and checks again for a check-in before delete. Check-in takes the same person lock first. SQLite in PHPUnit cannot interleave two connections on `:memory:`, so the regression test is sequential. The lock order is the PostgreSQL invariant.
- Rows that existed before this policy are repaired by `php artisan orbit:data:backfill-workforce-v1`, which calls `LegacyWorkforceBackfill` and is safe to run again. Schema migrations do not run that repair. `orbit:data:backfill-leave-periods` fills only an unset balance period, and `orbit:data:backfill-leave-requests` fills only a request that has no day count yet. `orbit:data:backfill-shift-clocks` copies a clock only onto an assignment that does not have one, and only from a shift in the same organisation. A request with no policy is pinned to a January calendar-year policy and that year's balance, not to a policy created later. `pending_days` is set to the sum of submitted `day_count` values for that person, type, and period. `entitled_days` is not rewritten. When those committed days already exceed `entitled_days + adjusted_days`, the excess is a `leave_adjustments` row with no acting user, and `adjusted_days` increases by that excess. The original entitlement stays the historical figure. A second run does not add another adjustment once the check holds. An attendance row with no assignment is linked when that person has exactly one published assignment that day, or when the check-in time falls inside exactly one of several. An ambiguous row stays unlinked and still blocks a second check-in for that date. Cancelling a request with no policy restores the existing calendar-year balance and does not create one.

## Consequences

- Rosters are generated from patterns in stretches of at most 62 days, not inferred on every check-in. Pattern apply walks staff in chunks and does not stop at a fixed headcount.
- Half-day leave, a generated rotation beyond pattern apply, a public API, and a person-specific non-working calendar are not part of this decision. A person-specific day off is an unassigned future period, or leave.
- Line-manager and department-head approval apply when those relationships are set. Otherwise an approver with `leave.approve` can decide. A `leave.policy` holder remains an override after self-approval is checked.
- Run `php artisan db:seed --class=Database\\Seeders\\RolesAndPermissionsSeeder` after deploy so organisation administrators receive `leave.policy`.
