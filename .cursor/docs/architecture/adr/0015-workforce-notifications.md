# ADR-0015: Workforce notifications and communication

- Status: Accepted
- Date: 2026-11-10

## Context

Schedule, leave, and attendance already call `WorkforceNotifier`. That notifier queues `DeliverWorkforceNotice`, which restores the tenant, sends a Laravel database and mail notification, and can hand SMS to the platform transmitter from ADR-0012. Push is bound to `NullPushNotifier`.

That path was enough for a few events. It did not give a person an inbox, a way to opt out of optional notices, a tenant-wide channel policy, or a place to change wording without editing PHP. Leave decision notes were also being copied into message bodies.

ORBIT owns the communication capability. The tenant owns the communication policy. Leave, schedule, and attendance keep their own business rules. A failed mail or SMS provider must not undo an approval, an assignment, or a recorded attendance row.

## Decision

- One application event becomes one `WorkforceMessage`. The business service finishes its transaction, then `WorkforceNotifier` dispatches `DeliverWorkforceNotice` with `afterCommit()`. The queue connection's `after_commit` flag stays false. The job opts in, so a rolled-back transaction does not leave a job, including when the test suite uses the sync driver.
- The job carries `organizationId` and restores that tenant. It loads the recipient and returns without sending when that user's organisation is not the job's organisation.
- Channels for this milestone are the in-app inbox (`database`), email (`mail`), and SMS. SMS is `SmsTransmitter` from ADR-0012. Business code does not call a vendor SDK. Push remains the null plug. WhatsApp is not implemented. A later channel is another branch in `WorkforceNotifier::deliver()` and, when it is a Laravel channel, in `WorkforceMessage::via()`. Leave, schedule, and attendance do not change to add it.
- `WorkforceEvents` is the catalogue. Each event has a category (`leave`, `schedule`, `attendance`, or `announcements`), a mandatory flag, and a reminder flag. Unknown events send nothing.
- `CommunicationPolicy` is one row per organisation, created when an administrator saves it. Reading it does not insert a row. Defaults keep email, SMS, in-app, leave, schedule, attendance reminders, and announcements on. SMS still stays off for an event until that event's organisation channel row turns it on. The policy master switch can turn a channel or a category off for everyone, including a mandatory event.
- `UserNotificationPreference` is one row per user and category. It can turn mail, in-app, or SMS off for optional events only. Mandatory events ignore that row. The tenant policy still applies to mandatory events.
- Mandatory events: `attendance.rejected`, `attendance.missing_checkout`, `schedule.published`, `schedule.changed`, `leave.submitted`, `leave.amended`, `leave.decided`, `field.assigned`. Optional events: `attendance.confirmed`, `attendance.late`, `attendance.missed`, `session.opened`, `schedule.reminder`, `leave.balance_warning`, `leave.pending_reminder`, `leave.balance_expiring`, `field.alert`. The reminder flag, which also requires `attendance_reminders_enabled`, is only on `schedule.reminder` and `attendance.missed`. Leave reminders follow `leave_notifications_enabled` only. `announcements` has a policy flag and a preference category and no events yet.
- Copy defaults live next to the event. A `notification_templates` row for that organisation, event, and channel `all` replaces the subject and body. `NotificationCopy` substitutes `{{a-z0-9_}}` tokens from a server-built map, drops every other `{{...}}` token, and strips `<?`, `{!!`, and `@php`. Values are scalars trimmed to 300 characters. Nothing is evaluated.
- `workforce_notice_deliveries` is unique on recipient, dedupe key, and channel (`notice`, `sms`, `push`). Status is `queued`, `sent`, or `failed`, with `failure_kind` and `attempts`. A `sent` row, or a `failed` row whose kind is `permanent` or `invalid_configuration`, is not sent again. A `queued` row left by a crashed worker can be claimed again. A retryable failure deletes the claim and rethrows so the queue can retry. Kinds: `InvalidPhoneNumber` and `PermanentSmsException` are permanent; `RetryableSmsException` is temporary; `InvalidArgumentException` is invalid configuration; a class name containing `RateLimit` is rate limited; anything else is unknown. Temporary, rate limited, and unknown are retried. Permanent and invalid configuration are not.
- The job allows 3 attempts, times out at 30 seconds, and backs off 30, 120, then 600 seconds. On the sync driver a provider exception is reported and swallowed so a successful HTTP action is not turned into an error page. The sync driver cannot defer that retry. Production `QUEUE_CONNECTION=database` must run a worker, documented in `implementation/workforce-notifications.md`.
- Mail and the in-app row share the `notice` claim and one `notify()` call. If that call throws after the in-app row is stored, the claim is removed and a later attempt can insert another in-app row and send another email. Mail has no provider idempotency key. SMS uses the same dedupe key as `sms_messages.idempotency_key`. Provider HTTP retries stay inside `DeliverSmsMessages`. A workforce delivery is marked `sent` for SMS once `transmit()` has accepted the handoff. An invalid phone is marked `failed` / `permanent` and does not insert an `sms_messages` row.
- Dedupe keys name the business fact, not a timestamp: `leave-submitted-{request}`, `leave-amended-{request}-{start}-{end}`, `leave-decided-{request}-{status}`, `leave-pending-{request}-{user}`, `leave-balance-{balance}-{available}`, `leave-expiring-{balance}-{period end}`, `schedule-published-{assignment}`, `schedule-removed-{assignment}`, `schedule-reminder-{assignment}`, `attendance-{record}-late|confirmed`, `attendance-rejected-{staff}-{local date}-{reason}`, `attendance-missing-{record}`, `attendance-missed-{assignment}` and `attendance-missed-{assignment}-manager-{user}`, `session-opened-{session}-{user}`, `field-assigned-{assignment}`, `field-alert-{activity}-{local date}`. The stored key is truncated to 80 characters. The field-alert date is the organisation's calendar day, together with the activity id.
- Recipients are resolved on the server. Leave submit, amend, and withdraw go to the same approver query the leave module already uses, excluding the requester. Approve, reject, and cancel go to the requesting employee. A low balance (2 days or fewer remaining) and an expiring balance go to that employee. A schedule assignment or removal goes to that staff member. An accepted or late attendance record, a missing check-out, and a rejected self check-in go to that staff user. Rejected check-in is notified only when the actor is that user, once per staff member, local date, and reason, and only for geofence, leave, device, manual, location, and method failures. Token expiry, duplicates, and OTP failures are not notified. A missed published shift notifies that person and, when different and in the same organisation, the line manager. A session opening notifies active users in that organisation who have `attendance.record`, in chunks of 100. No controller accepts a browser-supplied recipient as authority.
- The inbox is owned by the `User`, through Laravel's `notifiable` morph. A staff record, and a future student record, is how a business module finds that user. The notification tables do not point at `staff_members`. There is no student sign-in yet, and no separate student inbox. A later student who is an organisation user is addressed by passing that `User` into the same notifier. Which workforce event goes to which person stays a workforce rule.
- Unread is `notifications.read_at` null. Read is `read_at` set to a timestamp. There is no extra status word for that flag. `notification_read_audits` records who read which notice and when: `organization_id`, `notification_id`, `user_id`, `read_at`, unique on those three ids. The first transition from unread to read inserts one row. A repeated click, and mark-all over a notice that is already read, does not insert another. Mark-all selects unread ids in chunks and inserts those audits in bulk. Notices that were already read when this table was created are copied once from the stored `read_at`. The activity log remains the audit for policy, channel, preference, and template changes. It cannot enforce one read per user per notice, so the read trail is this table.
- Delivery status on `workforce_notice_deliveries` (`queued`, `sent`, `failed`) is independent of `read_at`. An SMS row can be `failed` while the in-app notice is unread, or `sent` after the person has read the inbox row.
- The header bell opens a list of the five newest notices, shows the unread count as text, and marks a notice read when it is opened. The action URL is taken from the stored payload, then accepted only by `Inbox::safeUrl`. The destination route still authorises the user. A missing page returns that page's not-found response. "View all" opens the paginated centre. Mark one and mark all are on that page.
- The inbox is `Inbox`. It filters `notifiable` and `organization_id`, pages 15 rows, and counts unread with `COUNT` on `read_at` without selecting the payload. The browser cannot submit a recipient id. A notice uuid from another user or another organisation is not found, and no read audit is written.
- Audited changes, without message bodies or secrets: `notifications.policy_updated`, `notifications.channels_updated`, `notifications.preferences_updated`, `notifications.template_updated`, `notifications.template_cleared`.
- There is no public notification API. A later mobile client should call `Inbox` and the existing preference, policy, and template actions. It should not talk to a provider.

## Consequences

- `php artisan workforce:remind` at 17:00 queues the next day's shift reminder, yesterday's missed attendance, leave submitted at least 2 days ago, and balances that end within 14 days and still have a day left. Shift reminders claim `reminded_at` before send, including when the person has opted out, so the same assignment is not reconsidered. The other reminders rely on the dedupe key. `workforce:field-status` is unchanged.
- A shift-template edit does not notify. Assignment clocks are a snapshot, so a "time changed" message would be false. Removal is the `schedule.changed` event.
- Decision notes, passwords, tokens, OTP values, and provider credentials are not placed in subjects, SMS, audit properties, or delivery rows.
- The announcements category is reserved. No announcement is sent.
- Run a database queue worker and the scheduler in production. The test suite uses the sync driver and does not prove a worker process.
